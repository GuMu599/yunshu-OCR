# 表格识别强化方案（已实现）

> 状态：**已实现并提交**（commit `1880573`）。本文件保留为设计溯源，落地代码见：
> `pdf2md/tables.py`（策略阶梯 + 几何重建）、`pdf2md/table_html.py`（Table 模型）、
> `pdf2md/table_model.py` + `models/production/table-adapter/`（SLANet 引擎）、
> `pdf2md/teds.py` + `pdf2md/benchmark.py`（度量与基准）。

| 方案 | 状态 | 说明 |

**实测**：92 测试全绿；基准 recall 1.0 / 结构 TEDS 0.97 / 质量门控准确率 1.0。

**重要发现**：Blundell 语料中 YOLO 标记的 10 个"表格"区域经 OCR 核验**没有一个是真数据表**——全是图表坐标轴标签、图例、目录列表或乱码图像。"表格识别不出来"的部分根因是 **YOLO 图/表误分类**（版面分类层问题），而非表格提取失败。阶梯对这些区域多数正确降级为图片。

**已实现与分析的差异**：
1. 阶梯顺序改为**几何优先、PyMuPDF 兜底**（原分析 PyMuPDF 优先）——实测 PyMuPDF lines 策略在无框/边线错位时产出幻影列。
2. 结构模型**不作优先升级**（原分析建议复杂表升级）——合成无框表上模型输出劣于几何，质量门保证其仅作最后兜底。
3. `_model_quality` 增加 ≥2×2 维度门，防图注/轴标签被模型误建成表格。

## 遗留

- 真实复杂表样本（合并单元格/多级表头）缺失，模型增益尚未用真实语料验证——有样本后加入基准并调阶梯。
- YOLO 图/表误分类需版面层调优（`table` 类阈值/置信度），属后续工作。

## 1. 现状与根因（已实测验证）

### 1.1 当前管线

```
YOLO 版面检测 (layout.py) ──"table" 区域
   ├─ find_table_ruled()   PyMuPDF find_tables, lines/lines_strict 策略（需矢量网格线）
   │    └─ 成功 → to_markdown() → MD 表格
   ├─ looks_like_table_data() + find_table_text()  text 策略（需原生文字层）
   └─ 都失败 → 保存区域截图 → table_image（**内容完全丢失**）
```

### 1.2 实测数据（Blundell 语料，10 个被降级的表格区域）

| 页 | 原生文字 | 位图 | 矢量线 | 结论 |
|---|---|---|---|---|
| 6 | 0 词 | 1 | 0 | 纯图片表 |
| 15 | 0 词 | 2 | 0 | 纯图片表（且被 YOLO 切成两块） |
| 18 | 27 词 | 1 | 0 | 图片表（词来自周围文字） |

`find_tables()` 在 page17–19 实测 `found 0 tables`。**当前语料的真表格全是位图**，而 `lines`/`text` 策略分别依赖矢量网格线和原生文字层，两者都没有——所以这张表一张也识别不出来，直接降级成图。

### 1.3 两大症状 → 两个独立根因

| 症状 | 根因 |
|---|---|
| 表格识别不出来 | ① 图片表完全没走 OCR ② YOLO 表格召回不足/区域被切碎 |
| 每行内容有误 | ① 文字表被 `to_markdown()` 错位（列未对齐/单元格多行/右对齐数字时）② 图片表连文字都没有 |

**结论**：`find_tables()` 调参（方案 C）救不了图片表；图片表必须走"渲染 → OCR → 结构重建"或"渲染 → 结构模型 → 单元格 OCR"。而复杂表的合并单元格/多级表头，纯几何重建做不到，需要结构模型。

## 2. 目标架构：表格 = 定位 + 结构 + 内容 三段

```
YOLO 定位 (已有, 需增强)        结构重建 (Tier1 几何 / Tier2 模型)      内容识别 (RapidOCR 已有)
─────────────────────        ─────────────────────────────────        ────────────────────────
"table" 区域                  cell/行/列/span 关系                    每个 cell 的文字
   ↑ conf 下调+区域合并         ↑ 修 to_markdown 错位                      ↑ 高 DPI + 后处理
```

关键认识：**定位、结构、内容三者解耦**。YOLO 只负责"表在哪"，结构负责"有哪些 cell、怎么合并"，内容负责"每个 cell 写了什么"。当前代码把结构和内容绑死在 PyMuPDF 的 `to_markdown()` 上，是根因。

## 3. 分层方案

### Tier 0 — 度量与基准集（最先做，否则无法判断强化是否有效）

- **指标用 TEDS**（Tree Edit Distance based Similarity），表格结构识别领域的标准指标，比"单元格级编辑距离"更能反映合并单元格/结构对错。SLANet 在 PubTabNet 上约 95% TEDS 即此指标。
- **基准集**：从真实 PDF 抠出 15–30 个表格，人工标注期望 HTML/MD（含合并单元格标记）。存 `tests/benchmarks/tables/`。
- 用"表格召回率（YOLO 命中）"、"结构 TEDS"、"单元格字符级编辑距离"三指标量化现状与改进。

### Tier 1 — 零模型：几何坐标重建（推荐先落地）

**目的**：不引入任何新模型，直接修复"文字表内容错位"，并让**简单图片表**也能转 MD。

**算法（两处复用同一套）**：
1. 拿到词级坐标：原生文字表用 `page.get_text("words")`；图片表用 **RapidOCR det 返回的 bbox + rec 文本**（`models/production/rapidocr-adapter` 的 det 本来就输出框）。
2. **行聚类**：按 y-center 排序，容差 ≈ 中位行高 × 0.6，合并为行。
3. **列聚类**：跨所有行收集 x0/x1 边界，聚成全局列边界；每行文本按与列边界重叠分配。
4. **数字列右对齐修正**：一列若 >60% 是数字且多数右对齐（x1 对齐），用 x1 校准列边界——直接修掉 `to_markdown()` 的经典错位。
5. **多行单元格**：同一格内多行文本保留换行，MD 中可用 `<br>` 或空格归一化（可配）。
6. 与 `find_tables()` 输出做覆盖评分（行列数×文本命中），择优。

**接入点**：`pdf2md/tables.py` 新增 `rebuild_table_from_boxes()`；`pipeline.py` 的 table 分支在其之前/替代 `find_table_ruled`。

**能力边界（诚实评估）**：合并单元格/多级表头**推断不了**，只能靠弱启发式（行内大空隙 + 上下行同位内容）猜，不可靠——所以复杂表必须靠 Tier 2。

### Tier 2 — 结构模型：RapidTable / SLANet（复杂表真正的解法）

**模型选型（已核实 2026 生态）**：

| 方案 | 说明 | 适配本项目？ |
|---|---|---|
| **RapidTable**（RapidAI） | SLANet ONNX，中/英各 ~7.4MB，输出 HTML（含 rowspan/colspan），依赖 rapidocr_onnxruntime，与 vendored RapidOCR 同源同工具链 | ✅ 首选，目录结构与 rapidocr-adapter 同构 |
| SLANet 原版 ONNX（社区导出） | PaddleOCR PP-StructureV2 时代，PubTabNet TEDS ~95% | ⚠️ 可用但集成成本高于 RapidTable |
| PP-StructureV3（SLANeXt + 单元格检测 RT-DETR） | 最新、最强，但走 Paddle 推理、GPU 导向（A100 峰值 37GB 显存） | ❌ 不符 CPU 轻量离线约束 |

**数据流**：
```
YOLO table 区域
  → 渲染高 DPI (≥300) 表格图
  → RapidTable/SLANet → cell bbox 列表 + HTML 骨架（含 rowspan/colspan）
  → 每个 cell 裁图 → RapidOCR rec → 回填
  → HTML → Markdown（合并单元格按 §4 决策做有损表达）
```

**接入点**：新增 `models/production/table-adapter/`（镜像 rapidocr-adapter 结构：onnx 权重 + 配置 + 推理封装），`pdf2md/tables.py` 增加 `find_table_structured()`。

**两个优势**：① 无框/无线表也能重建（结构从文字布局推断）；② 合并单元格、多级表头有显式 span 输出。SLANeXt 无线表专用权重进一步覆盖无框复杂表。

### Tier 3 — 复杂表专项

1. **跨页表格合并**：按列模板（列数+表头相似度）把相邻页同表拼合，表头只留第一段。README 里 v2 计划的落地。
2. **YOLO 表格召回增强**：对 `table` 类单独降 conf（如 0.15）；检测同一张表被切成多个相邻 region 时合并（page15 实测被切两块）。此改动同时惠及 Tier1/2。

## 4. 关键决策点：Markdown 无法表达合并单元格 ⚠️

MD 表格**没有 rowspan/colspan 语法**。复杂表转 MD 必然有损，这是绕不开的设计决策，候选：

| 方案 | 描述 | 取舍 |
|---|---|---|
| A. 展开复制 | 合并的头部文本在每个跨越行重复出现 | 数据完整、MD 可读性差、冗余 |
| B. 空白占位 | 首次出现保留文本，后续行留空 | 形状还原、最接近手写 MD 习惯、但阅读时要纵向对齐才知道含义 |
| C. HTML 旁路 | **layout.json 存完整 HTML（真实来源）**，MD 用 A 或 B 有损表达，并加注释 `<!-- table 完整结构见 layout.json -->` | 溯源不丢、MD 保持可读、AI 需完整结构时可查 HTML |

**推荐 C 为主**（layout.json 早已是溯源载体，顺理成章）：MD 是"给人/AI 快速消费"的有损视图，layout.json 的 HTML 是"机器完整消费"的真实来源。若用户常导出 Excel，可再加 xlsx 旁路。

---

## 5. 内容纠错专项

- **图片表渲染 DPI ≥ 300**：当前 `image_dpi=200` 仅用于截图，OCR 路径需更高 DPI（公式已用 300 的先例）。
- **单元格级 OCR + 置信度标注**：沿用现有 `formula_uncertain` 模式——低置信 cell 记入 layout.json，不打断主链路。
- **数字列后处理**：Tier1 的右对齐修正同样用于 OCR 结果。
- **文字层与 OCR 交叉验证**：同一区域既有原生文字又有 OCR 时以原生为准；原生缺失才用 OCR。
- **RapidOCR 英文丢空格**（README 已知问题）：单元格级处理时用空格重建（相邻 box 间距判词边界）。

## 7. 风险与回退

- **RapidTable 中文权重**：需要确认随包/下载方式（英文权重随 pip 包内置，中文需单独下）——与当前 rapidocr-adapter 的权重落地方式（本地目录 + gitignore）一致即可。
- **结构模型单表耗时**：SLANet 推理 + 逐 cell OCR，复杂表可能数秒/张。可加"仅当 Tier1 判为复杂表才走 Tier2"的策略阶梯控成本。
- **有损表达争议**：合并单元格的 MD 表示若无共识，先默认 B（空白占位）并保证 HTML 旁路完整。
- **回退安全**：Tier1/2 产出可疑时（列数异常、TEDS 低），回退到 table_image 截图 + 标记，不劣于现状。
